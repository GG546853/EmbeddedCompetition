逐 epoch HW/SW 计时实测
日期：2026-11-05
主题：给 AI 推理补逐 epoch block 计时，用实测数据核对简历里的三项指标

============================================================
一、背景与目标
============================================================

1. 原简历句
------------------------------------------------------------
「边缘 AI 与 NPU 优化：在 MCU 内置 NPU 部署 BlazeFace + MobileFaceNet，
完成 int8 量化、anchor 解码 + NMS、时域平滑与阈值调优；
CPU 回退 epoch 110→13，NPU 占比 40%→93%，单帧 72→41 ms。」

2. 问题
------------------------------------------------------------
- 110→13、93%、72→41 ms 三组数字都是为写简历推测的，没有任何实测出处；
- 原插桩只统计 epoch 个数（profiling.c 的 ep sw/hw/hyb/in），
  没有逐 epoch 计时，所以「通过 epoch 级 HW/SW 计时定位」不成立；
- 仓库里没有 .tflite/.onnx，模型侧换算子与重新量化无法在本仓库完成，
  13 / 93% 也无法在本地复现。

3. 本轮目标
------------------------------------------------------------
不改模型、不做优化，只把现状测准：
- 在每个 epoch block 的 PRE_START / POST_END 之间取 DWT 周期数，
  按 SW / Hybrid / Internal / HW 四类累计；
- 分别测检测路径（BlazeFace）和识别路径（MobileFaceNet）；
- 用实测值判定简历三项数据，并给出只有实测支撑的替换句。

============================================================
二、口径定义（先定义，后给数字）
============================================================

1. graph epoch 与 runtime epoch block
------------------------------------------------------------
- 生成报告（network_f_generate_report.txt、network_fc_generate_report.txt）
  统计的是 graph epoch；
- 板上回调（LL_ATON 的 PRE_START/POST_END）统计的是 runtime epoch block，
  一个 graph epoch 可能拆成多个 block。
- 两者分母不同，不能直接相减。network_fc 恰好 183 = 183，可逐项对照；
  network_f 则是 95 个 graph epoch 对 115 个 runtime block，只能各说各的。

2. 计数占比与时间占比
------------------------------------------------------------
- 计数占比 = 该类 block 数 / 总 block 数；
- 时间占比 = 该类 ept 累计 / 四类 ept 累计。
- 原简历的「40%」是计数占比（73/183），不是时间占比；
  两者在本模型上差别很大，文中一律注明用的是哪一种。

3. ep hw 与 ept hw 不是同一个东西
------------------------------------------------------------
- 计数行 `ep sw=… hw=… hyb=… bl=… in=… /frame` 里，
  `hw` 沿用旧语义：**所有非 SW block**，包含 hybrid 与 internal；
  因此 sw + hw = 总 block 数。
- 计时行 `ept sw=… hw=… hyb=… in=… us/frame` 里，四类**互斥**：
  SW → ept_sw，否则 Hybrid → ept_hyb，否则 Internal → ept_in，
  其余 → ept_hw（纯 HW）。
- 由计数可反推纯 HW 个数：纯 HW = ep_hw − ep_hyb − ep_in。

4. 两条路径的统计口径
------------------------------------------------------------
- 检测「单帧计算」= cin + cout + pre + infer + cmd + draw + dstop + tail，
  **不含 wait**（wait 是等相机帧，不是算力消耗）；
- 识别以 `[PROF fc] wall` 为准（纯网络推理时间），
  `[PROF AI] reid` 是包含特征匹配等应用侧开销的整段耗时；
- 统计窗口：检测 9 个窗口，识别 5 个含 fc 推理的窗口。

============================================================
三、数据有效性校验
============================================================

1. 识别路径：block 数与生成报告一致
------------------------------------------------------------
- 板上（2026-11-05-ai-reid-epoch-timing.txt 的 5 个窗口）：`ep sw=107 hw=76 hyb=3 in=0`
  → 总 block 107 + 76 = 183；
  → 纯 HW = 76 − 3 − 0 = 73；
  → 107 纯 SW + 3 hybrid = 110，与报告的 110 个 SW epoch 吻合
    （hybrid 块内包含 SW 部分）。
- 报告出处：network_fc_generate_report.txt:395
  「Total number of epochs: 183 of which 110 implemented in software」。
- 结论：fc 的 block 配对正确，可以用。

2. 检测路径：分母不同，分开表述
------------------------------------------------------------
- 板上：`ep sw=5 hw=110 hyb=22 in=22` → 总 block 115；
  纯 HW = 110 − 22 − 22 = 66。
- 报告：95 个 graph epoch，其中 26 个 SW
  （network_f_generate_report.txt:229）。
- 115 ≠ 95，因此本文不把报告里的 26 与板上的 5 相减；
  检测路径只使用板上实测值。

3. 时间闭合（ept 之和应接近 wall）
------------------------------------------------------------
  路径    ept 四类之和   wall      差值
  ------  ------------  --------  -------
  检测     15231 us      15950 us  719 us
  识别    170693 us     171367 us  675 us

- 差值来自 init/deinit/post 与 block 之间的固定开销，均 <1 ms；
- 识别路径另有 `call + wfe = 149388 + 21662 = 171050 us`，
  与 wall 171367 us 差 317 us，两条独立路径互相印证。
- 结论：计时点成对出现，没有漏配或重复配对。

4. 空窗口
------------------------------------------------------------
- 2026-11-05-ai-reid-epoch-timing.txt 中有 2 个窗口（第 73-75、167-169 行）`it=0` 且所有 PROF 值为 0，
  但 `p1` 仍推进 66 帧；两个窗口的 wall 分别为 1055 ms 量级，
  AITask 未进入统计。
- 这两个窗口不含任何可用数值，不参与统计，也不影响 5 次 fc 的配对结果。
  成因未进一步追查（与本文指标无关）。

============================================================
四、检测路径实测（BlazeFace，9 个窗口）
============================================================

1. 单帧耗时（均值）
------------------------------------------------------------
  阶段        均值        最大值范围
  ----------  ----------  ----------
  wait        13.97 ms    14.52-14.72 ms
  cin         0.023 ms
  cout        0.093 ms
  pre         2.077 ms    2.097-2.101 ms（196 KB u8→f32）
  infer       15.952 ms   16.020-16.139 ms
  cmd         0.001 ms
  draw        0.351 ms
  dstop       0
  tail        0.539 ms
  ----------  ----------
  单帧计算     19.04 ms    （不含 wait）
  整帧周期     33.0 ms     （含 wait，约 30 fps）
  wall        15.950 ms    （与 infer 一致）

  说明：
  - infer 与 wall 差 0-3 us（计时点位置），沿用上一份校准的结论；
  - 检测路径的 NPU 推理 15.95 ms/帧，其中纯 HW 时间 11.16 ms、
    WFE 11.00 ms/帧，说明这 15.95 ms 里 NPU 大部分时间在计算；
  - 196 KB 转换实测 2.08 ms/帧，确实存在，本轮没有消除。

2. epoch block 分布与时间占比
------------------------------------------------------------
  block 数（每帧）：
    纯 SW 5 + Hybrid 22 + Internal 22 + 纯 HW 66 = 115

  时间（每帧，四类互斥，合计 15.231 ms）：
    类别        耗时        时间占比
    ----------  ----------  --------
    SW           0.817 ms     5.4%
    Hybrid       0.742 ms     4.9%
    Internal     2.517 ms    16.5%
    纯 HW       11.155 ms    73.2%

  解读：
  - 检测路径是 NPU/硬件主导：纯 HW 占 73.2%，
    加上同样由 ATON 硬件执行的 internal（16.5%）与 hybrid，合计约 95%；
  - internal 是 runtime 的内部 epoch block，执行时同样设置 wait mask
    等硬件完成（ll_aton_runtime.c:118），不属于 CPU 回退；
  - SW 只有 5 个 block、0.82 ms，检测模型的 CPU 回退不是瓶颈。

============================================================
五、识别路径实测（MobileFaceNet，5 次 fc 推理）
============================================================

1. 单次耗时
------------------------------------------------------------
  指标            均值        窗口范围
  --------------  ----------  --------------------
  wall            171.37 ms   171.13-171.85 ms
  init            0.090 ms
  deinit          0.001 ms
  call            149.39 ms   149.16-149.86 ms
  wfe             21.66 ms    21.65-21.68 ms
  post            0.006 ms
  reid 阶段       190-210 ms   最大单次 216 ms（含特征匹配）

  说明：
  - call + wfe ≈ wall，说明 runtime 调用里 CPU 占 149 ms、等 NPU 占 21.7 ms；
  - `[PROF AI] reid` 按「窗口内 reid 总时间 / fc 次数」折算，5 个窗口为
    190-210 ms/次（均值约 201 ms），比 fc 的 171 ms 多出约 20-40 ms
    的特征匹配/应用侧开销。

2. epoch block 分布与时间占比
------------------------------------------------------------
  block 数（每次推理）：
    纯 SW 107 + Hybrid 3 + Internal 0 + 纯 HW 73 = 183

  时间（每次推理，四类互斥，合计 170.693 ms）：
    类别        耗时         时间占比
    ----------  -----------  --------
    SW           143.162 ms    83.9%
    Hybrid         0.448 ms     0.3%
    Internal       0 ms         0
    纯 HW         27.082 ms    15.9%

  平均每 block：
    SW       143.162 / 107 = 1.338 ms
    Hybrid     0.448 /   3 = 0.149 ms
    纯 HW     27.082 /  73 = 0.371 ms

  解读：
  - 识别路径与检测路径相反，是 CPU 主导：SW 时间占 83.9%，
    NPU 纯 HW 只占 15.9%；
  - SW 平均每个 block 1.34 ms，是纯 HW block 的 3.6 倍，
    说明瓶颈不是 block 数量，而是每个回退 block 的计算量；
  - 回退 epoch 的算子构成（生成报告，共 110 个）：
      DequantizeLinear 37、QuantizeLinear 33、PReLU 33、
      Conv 3、Cast 3、BatchNormalization 1；
    量化/反量化与 PReLU 合计 103 个，占 94%，
    与 PReLU 的逐元素 CPU 开销一致。

3. 计数占比与时间占比对照
------------------------------------------------------------
  口径              NPU（纯 HW）     CPU（纯 SW）
  ----------------  --------------  --------------
  block 计数占比     73/183 = 39.9%  107/183 = 58.5%
  时间占比           15.9%           83.9%

  - 「40%」对应的是第一行，成立；
  - 真正决定单次耗时的是第二行，CPU 回退占 84%；
  - 若把 hybrid 中的 SW 部分也算进 CPU，CPU 占比还要更高。

============================================================
六、对原简历数据的判定
============================================================

  说法              判定        依据
  ----------------  ----------  ------------------------------------------
  110 个 CPU 回退   成立        报告 110/183；板上 107 SW + 3 hybrid
  110→13            无出处      13 从未实现，仓库无模型源文件可做
  40%               成立        73/183 = 39.9%，但是 **block 计数占比**
  40%→93%           无出处      93% 未测到；当前基线按时间只有 15.9% NPU
  单帧 72 ms        无出处      检测整帧周期实测 33.0 ms（计算 19.0 ms）
  单帧 41 ms        无出处      识别实测 171.4 ms，检测 19.0 ms，均非 41
  196 KB 转换       成立但未消除  AI_task.c:579-584 每帧执行，实测 pre 2.08 ms

  结论：原句把「检测路径的帧耗时」和「识别路径的单次推理」混在了一起，
  且把计数占比当成了算力占比；13 / 93% / 72→41 ms 没有实测支撑，全部删除。

八、复现
============================================================

1. 代码开关：profiling.h 的 PROFILING_ENABLE 保持 1；
2. 构建（PATH 需加 CubeIDE 的 make 与 GCC 13.3）：
   make -C ElectronicWarehouse/Appli/Release all -j8，确认 EXITCODE=0；
3. 检测路径：相机页、画面持续有人脸，抓约 60 s，
   确认 `[PROF f]` 行出现 `ept` 字段；
4. 识别路径：有脸时触发 1:N 识别 5 次，
   确认 `[PROF fc] n>0`；
5. 日志：检测见 docs/logs/2026-11-05-ai-detect-epoch-timing.txt（9 个窗口），
   识别见 docs/logs/2026-11-05-ai-reid-epoch-timing.txt（5 个含 fc 的窗口）。

   更细的每 block 波动未统计；
2. network_f 的 graph epoch（95）与 runtime block（115）未做逐项映射，
   检测路径只用板上值；
3. 2026-11-05-ai-reid-epoch-timing.txt 两个 it=0 空窗口的成因未追查（不含数值，不影响结论）；

   重导出后可直接复用本基座测「优化后」数据。
