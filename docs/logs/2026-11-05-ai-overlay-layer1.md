优化日志
日期：2026-11-05
主题：AI 检测框改画到 LTDC 图层 1（消除每帧 PIPE1 停流与框缺角）

============================================================
一、背景与目标
============================================================

1. 现象
------------------------------------------------------------
- 相机页检测到人脸后，绿色检测框和 6 个关键点出现「缺角」，
  框的下半部分时有时无，伴随约 30 Hz 的闪烁。
- 2026-10-22 的 P0-1 运行时统计与本次新增的阶段统计给出了证据：
  人脸上画面时 AITask 占 98% CPU、IDLE 为 0%，每帧有 14 ms
  花在「停相机」上。

  基线数据（2026-11-04-ai-face-present-pipe1-stop-baseline.txt）：

      [PROF AI] it=1227 ... wait 6/12 cin 23/30 cout 100/103
                pre 2076/2111 infer 15850/16024 cmd 1/41 reid 2/39
                draw 134/163 dstop 14333/25277 tail 514/2477 us(avg/max)

2. 原始实现
------------------------------------------------------------
- 绘制函数在画框前后各调用一次 HAL_DCMIPP_CSI_PIPE_Stop/Start，
  目的是「暂停采集，避免框被下一帧覆盖」。
- 框直接用 DMA2D R2M（RGB888）画进 g_ltdc_framebuf，也就是
  LTDC 图层 0，而 DCMIPP PIPE1 正在连续写同一块 buffer。
- 停止/重启 PIPE1 每次约 14 ms，占 33 ms 帧周期的 42%。

3. 目标
------------------------------------------------------------
- 相机不停流（dstop = 0）；
- 检测框完整、无缺角、无闪烁；
- 不新增采集缓冲，不改链接脚本、DCMIPP 与 LTDC 配置。

============================================================
二、先做的最小验证实验
============================================================

在动结构之前，先只删除绘制路径上的 PIPE1 Stop/Start 两行，
其余保持不变，确认「停流」与「缺角」是不是同一个原因。

结果：
- dstop 归零，draw 从 13.7 ms 降到 131 µs；
- 但框仍然缺角、仍然闪烁。

结论：停流只是 CPU 浪费的来源，不是缺角的来源。
框被覆盖的根因是它与采集共用同一块 buffer：

- 帧信号量在 PIPE2 写完时释放，AI 循环随即开始；
- 预处理 2.08 ms + 推理 15.85 ms，框在帧开始后约 18.6 ms 才画出；
- 此时 DCMIPP 已写完约 18.6 / 33 ≈ 56% 的行；
- 本帧剩余 44% 的扫描会把框的下半部分重新写成画面内容。

因此无论是否暂停采集，只要框和采集写同一块内存，
「先画好、再被本帧剩余扫描覆盖」就一定会发生。

============================================================
三、方案取舍：为什么不是双缓冲
============================================================

1. 硬件约束
------------------------------------------------------------
- STM32N647 的 LTDC 只有 2 个图层（MAX_LAYER = 2）：
  图层 0：800×480 RGB888，g_ltdc_framebuf，摄像头 PIPE1 直写；
  图层 1：800×480 RGB565，g_ltdc_ui_framebuf，LVGL 使用。
- 面板 59.4 Hz（16.8 ms），相机 30.4 fps（32.9 ms），两者异步。

2. 双缓冲（DBM）的问题
------------------------------------------------------------
- 双缓冲解决的是「采集写 A 时，LTDC 显示 B」，但换址
  （VBR 重载）最晚要等一个场周期（16.8 ms）才生效；
- 期间 LTDC 显示的仍是被采集的那块，出现随时间漂移的撕裂带；
- 框仍在推理结束后才画，30 Hz 闪一下的问题也不会消失；
- 要完全干净需要 3 块缓冲 + 在相机 VSYNC 时刻由软件选择
  下一帧采集地址，需要改链接脚本、DCMIPP 地址切换与同步逻辑。

3. 选择：覆盖层（图层 1）
------------------------------------------------------------
- DCMIPP 只写图层 0，框写图层 1，物理上不可能被采集覆盖；
- LTDC 合成时框自然压在实时预览之上；
- 不新增缓冲、不改链接脚本、不改 DCMIPP/LTDC 配置；
- 代价：与 LVGL 共用图层 1，需要自己擦除上一帧的框。

============================================================
四、具体改动
============================================================

1. ElectronicWarehouse/Appli/APP/AI_task.c
------------------------------------------------------------
- 新增 extern g_ltdc_ui_framebuf 与 RGB565 宏：

      #define UI565(r,g,b)  ((((r)&0xF8)<<8)|(((g)&0xFC)<<3)|((b)>>3))
      #define BOX_COLOR565  UI565(0,255,0)
      #define OVERLAY_CLEAR 0x0000u
      #define OVERLAY_RECT_MAX 16

- fill_rect / draw_box / draw_kp 改为 ui_edge / ui_box / ui_kp：
  DMA2D R2M，DMA2D_OUTPUT_RGB565，写入 g_ltdc_ui_framebuf；
  先做与显示区求交的裁剪，再记录裁剪后的矩形。

- 新增擦除表：

      static int16_t s_rect[OVERLAY_RECT_MAX][4];
      static uint8_t s_rect_n;

- draw_detections_on_display() 改为「先擦后画」：
  1) 用上一帧的 s_rect 填 0x0000（黑色 = 颜色键透明）；
  2) 清空 s_rect_n，再画本帧的框与关键点并重新记录；
  3) 无检测时只擦不画。

- AI_Task 入口 s_rect_n = 0，避免线程重启后拿旧坐标擦除。

- 新增 ai_clear_overlay()，供外部在线程被终止后清理。

2. ElectronicWarehouse/Appli/APP/AI_task.h
------------------------------------------------------------
- 声明 void ai_clear_overlay(void);

3. ElectronicWarehouse/Appli/APP/ui/actions.c
------------------------------------------------------------
- 三处 osThreadTerminate(AITaskHandle) 之后调用 ai_clear_overlay()：
  action_action_stop_camera()、action_action_recognize() 的匹配
  与非匹配两个分支，避免硬杀线程后图层 1 残留绿框。

4. 明确不做：不创建 dma2d_mutex
------------------------------------------------------------
- actions.c 里的 dma2d_mutex 从未 osMutexNew，所有守护都是空操作；
  LVGL 的 flush 路径已经 acquire/release 它。
- 看似只差一次创建，但 AI 线程是被 osThreadTerminate 从 UI 线程
  任意时刻硬杀的：若恰好杀在持锁的几微秒内，FreeRTOS 不会自动
  释放，此后 LVGL 的 osMutexAcquire(osWaitForever) 永久阻塞，
  UI 直接卡死。保持现状（无锁、竞态概率低、后果只是局部花屏），
  把「协作式退出 + 真正启用互斥量」列为后续独立任务。

5. 不动的地方
------------------------------------------------------------
- run_reid_pipeline() 里的 PIPE1 Stop/Start（裁剪人脸时仍需）；
- cam_frame_sem 语义、DCMIPP/LTDC 配置、链接脚本、profiling 口径。

============================================================
五、原理要点
============================================================

1. 颜色键
------------------------------------------------------------
- 进入相机页时 actions.c 调用：
      HAL_LTDC_ConfigColorKeying(&hltdc, 0, 1);
      HAL_LTDC_EnableColorKeying(&hltdc, 1);
  图层 1 中等于 0x0000 的像素不参与合成，直接透出图层 0。
- 因此「擦除」= 往图层 1 填 0x0000，不需要保存背景。

2. 为什么框不可能被覆盖
------------------------------------------------------------
- DCMIPP 的写目标只有图层 0 的 g_ltdc_framebuf；
- 框只写图层 1，两者物理隔离；
- 采集可以在任意时刻写任意行，都不会影响框。

3. 擦除表为什么记录裁剪后的矩形
------------------------------------------------------------
- 框和关键点可能部分超出屏幕（负坐标、越界）；
- 擦除必须用与绘制完全相同的像素范围，否则会残留边角；
- ui_edge 先裁剪、后记录，保证「画哪擦哪」。

4. 帧内时序
------------------------------------------------------------
- 擦 + 画合计约 300 µs（max 425 µs），占帧预算 0.9%；
- 与改动前「停流 14 ms + 画 134 µs」相比，时间几乎可以忽略。

============================================================
六、测量结果
============================================================

1. 前后对比（两份日志都是画面中持续有人脸）
------------------------------------------------------------
  指标            基线（PIPE1 停流）      覆盖层版本
  ------------    --------------------    -------------------------
  dstop           14333/25277 us          0/0
  draw            134/163 us              285-346 us（max 425）
  wait            6/12 us                 14204/14796 us
  AITask          98%                     54-56%
  IDLE            0%                      27-33%
  LV_Task         1%                      4%
  帧率            ~30 fps                 30.7 fps（it=p1=p2）
  window          20-37 s                 1.16-1.28 s

说明：
- 基线的 window 远大于 1 s，说明低优先级 StatsTask 在 AITask
  占满 CPU 时被严重延迟；覆盖层版本回到 1.2 s 左右，与 1 s
  统计周期（PROF_PRINT_DIV = 2）相符。
- 帧率按「两个统计窗口累计的 it」核算：75 帧 / 约 2.5 s ≈ 30 fps；
  it、p1、p2 三者相等，说明 AI 循环与两路 PIPE 同步，没有丢帧。

2. 33 ms 帧预算拆分
------------------------------------------------------------
  wait      14.20 ms  43.0%   等下一帧（相机节拍）
  infer     15.85 ms  48.0%   NPU 推理
  pre        2.08 ms   6.3%   BGR→RGB + 归一化
  tail       0.50 ms   1.5%   循环尾部（含 vTaskDelay(1)）
  draw       0.30 ms   0.9%   擦 + 画
  cout       0.09 ms   0.3%   输出缓存处理
  cin        0.02 ms   0.1%   输入缓存处理
  cmd/reid   0.00 ms   0.0%   串口命令 / ReID（本帧无请求）

结论：推理是唯一大头；软件侧与绘制都已不是瓶颈。

3. NPU 内部拆解（network_f，每帧）
------------------------------------------------------------
  wall 15.88 ms = init 0.05 + call 4.22 + wfe 11.01 + post 0.46 ms
  - wfe 占 69.4%：大部分时间在等 NPU 硬件，软件侧无法加速；
  - call 占 26.6%：137 个 epoch 的调度与寄存器配置；
  - maxcall 628 us、maxwfe 657 us，最坏单次也远小于帧周期；
  - epoch 构成：sw 5 / hw 110 / hybrid 22 / blob 0 / internal 22，
    80% 的 epoch 完全跑在 NPU 上；
  - wfecalls 198，其中 99 次（50%）是 <100 cycles 的短唤醒，
    属于 LL_ATON 异步运行时的固有噪声，不是瓶颈。

4. 栈余量
------------------------------------------------------------
- AITask 高水位剩 6304 B（栈大小 8192 B），余量充足；
- LV_Task 剩 125480 B，稳定。

============================================================
七、结论与遗留
============================================================

已完成：
- 每帧 14 ms 的相机停流被完全消除，33 ms 帧预算里归还了 42%；
- 框与关键点不再经过采集缓冲，缺角/闪烁在物理上不可能再发生；
- AI 循环从「忙等」变为相机节拍驱动，CPU 占用从 98% 降到 55%；
- 每帧多出约 300 µs 的擦除开销，仍只占帧预算 0.9%。

遗留问题：
1. 与 LVGL 共用图层 1：控件重绘的 dirty area 会临时覆盖该区域的框；
   相机页 UI 很静态，实际影响很小。
2. dma2d_mutex 未启用：AI 线程与 LVGL flush 理论上可能同时操作
   DMA2D，概率低、后果是局部花屏；需要先解决「硬杀线程」问题。
3. 视觉延迟：框在推理结束后才画，仍滞后画面约一帧（33 ms）；
   要降到接近零延迟需要 3 缓冲 + VSYNC 选址，属另一个量级的改动。
4. 推理本身 15.85 ms 中 69% 是硬件等待，进一步提速只能换更小的
   模型、量化或降低输入分辨率。
