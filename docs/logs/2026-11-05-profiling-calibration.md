测量基座校准日志
日期：2026-11-05
主题：NPU 总耗时改用 DWT 周期数，并用 A/B 量化插桩开销

============================================================
一、背景与目标
============================================================

1. 为什么要校准
------------------------------------------------------------
- 把 AI 流水线拆成 wait / cin / cout / pre / infer / cmd / reid /
  draw / dstop / tail 之后，所有优化决策都建立在这些数字上；
- 如果测量工具本身精度不一、或者自己吃掉可观 CPU，
  「AITask 55%、IDLE 30%」这类结论就不可信；
- 因此先给测量基座本身标定两个量：一致性和开销。

2. 两个待补的缺口
------------------------------------------------------------
缺口一：精度不一致。
- 各流水线阶段（PROF_NPU_F 等）用 64 位 DWT 周期数计时；
- 唯独 NPU 总耗时 wall 用 1 ms 的 FreeRTOS tick 计时，
  单次测量的量化误差可达 ±1 ms，与分段不在同一量级。

缺口二：开销未知。
- profiling 的计数（__disable_irq 配对、累加）在每个阶段都执行；
- 每两个统计窗口还会额外打印 3 行 [PROF] 日志（阻塞串口）；
- 这两部分合计占多少 CPU，此前没有数据。

============================================================
二、缺口一：wall 改用 DWT 周期数
============================================================

1. 原实现
------------------------------------------------------------
- app_x-cube-ai.c 在推理前后各取一次 xTaskGetTickCount()：

      uint32_t wall0 = profiling_tick_now();          /* 1 ms 粒度 */
      ...
      profiling_npu_wall(PROF_NET_F, profiling_tick_now() - wall0);

- profiling.c 里累计 tick，再换算成每帧微秒：

      wall_ticks += ticks;
      return (uint32_t)((wall_ticks * (1000000u / configTICK_RATE_HZ))
                        / n->runs);

- 平均到几十帧后小数位看起来平滑，但每一帧的测量值本身被
  量化到 1 ms，和 infer 的周期级精度不可比。

2. 新实现
------------------------------------------------------------
- 首尾都改用 profiling_now()，即 getRunTimeCounterValue()
  返回的 64 位 DWT 周期数（与所有分段同一时间基准）：

      uint64_t wall0 = profiling_now();
      ...
      profiling_npu_wall(PROF_NET_F, profiling_now() - wall0);

- profiling.c 累计周期数，打印时统一除以 CYCLES_PER_US：

      wall_cycles += cycles;
      return (uint32_t)(n->wall_cycles / n->runs / CYCLES_PER_US);

- 顺带删除已无调用者的 profiling_tick_now()。

3. 前后对比
------------------------------------------------------------
同一场景、同一窗口内 [PROF AI] 的 infer 与 [PROF f ] 的 wall：

  修正前（2026-11-05-ai-face-present-overlay-layer1.txt）
    infer=15841 wall=15880 diff=+39 us
    infer=15836 wall=15851 diff=+15 us
    infer=15846 wall=15878 diff=+32 us
    infer=15849 wall=15800 diff=-49 us
    infer=15847 wall=15810 diff=-37 us

  修正后（2026-11-05-ai-face-present-wall-us.txt，11 个窗口）
    差值全部落在 -2 ~ -3 us，例如：
    infer=15870 wall=15867 diff=-3 us
    infer=15881 wall=15878 diff=-3 us
    infer=15869 wall=15866 diff=-3 us

说明：
- 修正前差值在 -49 ~ +39 us 之间逐窗漂移，是 tick 量化在
  平均后残留的误差；
- 修正后稳定在 -3 us。这 3 us 是两处计时的起止点不同
  （infer 在外层包住整个调用，wall 在内层），是固定偏移，
  不是测量误差；
- 由此 wall 与 infer 可以在微秒级互相印证：n=73-76 帧时
  wall≈15.87 ms，与 33 ms 帧预算中的 infer 完全一致。

============================================================
三、缺口二：A/B 实验设计
============================================================

1. 变量
------------------------------------------------------------
- 唯一变量：profiling.h 的 PROFILING_ENABLE（1 → 0）；
- 为 0 时 profiling_stage / profiling_now / profiling_print_window
  等全部展开为空操作，所有计数器和 3 行 [PROF] 日志一起消失；
- 其余代码、任务优先级、模型、场景完全相同。

2. 样本
------------------------------------------------------------
- 场景：相机页、画面持续有人脸；
- profiling ON：19 → 22 个统计窗口（2026-11-05-ai-face-present-wall-us.txt）；
- profiling OFF：19 个统计窗口（2026-11-05-ai-face-present-profiling-off.txt）；
- 串口 USART1 115200 8N1，每秒统计窗口打印 17 行任务表。

3. 观察指标
------------------------------------------------------------
- 各任务的 CPU 百分比（StatsTask 用 uxTaskGetSystemState 的
  运行时间差分计算，整数百分比）；
- --- window --- 的墙钟长度；
- 任务栈余量（高水位）。

============================================================
四、A/B 结果
============================================================

1. 任务占用
------------------------------------------------------------
  指标            ON        OFF       差值
  ------------    --------  --------  --------
  AITask          55.14%    55.05%    +0.09   （噪声）
  Stats            6.41%     4.89%    +1.52
  IDLE            29.82%    31.37%    -1.55
  LV_Task             4%        4%     0
  其它任务        0-4%      0-4%      无实质变化

  百分比是整数截断，单窗分辨率 1%；上表为窗口均值。

2. 窗口长度与栈
------------------------------------------------------------
  指标                 ON          OFF        差值
  ----------------     ----------  ----------  ---------
  window 均值          1222.8 ms   1163.1 ms   +59.7 ms
  Stats 栈余量         2672 B      3504 B      -832 B
  AITask 栈余量       2008 B      2008 B      0

  - 窗口变长只发生在打印 [PROF] 的周期：无 PROF 的窗口约
    1157-1160 ms，含 PROF 的窗口 1266-1343 ms，每两窗一次；
  - Stats 栈多占用 832 B，来自 profiling_print_window() 里的
    两个统计数组副本与打印缓冲，4096 B 栈仍余 2.6 KB。

3. 开销归因
------------------------------------------------------------
可测出的 1.5 个百分点全部落在 StatsTask，而不是 AITask：

- AITask 在做同样的推理与绘制，profiling_stage() 等计数
  也在它里面执行，但两份日志都是 55%，说明这部分开销
  低于 1% 的统计分辨率；
- StatsTask 的增量来自 3 行阻塞日志：

      [PROF AI]  167 B
      [PROF f ]  195 B
      [PROF fc]  167 B
      合计       529 B / 次

  每两个窗口打印一次（PROF_PRINT_DIV = 2，约 2.4 s），
  115200 8N1 的线速是 11520 B/s，529 B 约 46 ms 纯发送时间；
- 实际窗口拉长略大于 46 ms：StatsTask 是 osPriorityLow，
  发送期间被 AITask 抢占后 UART 无法及时供数，停走的时间
  也计入墙钟，所以平均每窗多出约 60 ms。

============================================================
五、结论
============================================================

1. 测量基座的一致性：完成
------------------------------------------------------------
- wall 与 infer 现在同为 64 位 DWT 周期数，差值为固定的
  -3 us（计时点位置），可以互相校验；
- 1 ms tick 引入的 ±1 ms 单帧量化已消除。

2. 测量基座的开销：约 1.5 个百分点
------------------------------------------------------------
- 总量：Stats 4.89% → 6.41%，IDLE 31.37% → 29.82%，
  AITask 无变化；
- 构成：可测部分几乎全部是那次阻塞串口打印，计数本身
  低于 1% 分辨率；
- 含义：对「infer 15.87 ms、AITask 55%、IDLE 30%」这类
  结论，插桩不改变判断；对比小于约 2% 的改动时需要考虑
  这层底噪。

3. 需要进一步降开销时的选项（当前不需要）
------------------------------------------------------------
- PROF_PRINT_DIV 2 → 4，日志开销减半；
- 三行合并为一行，减少行数与格式化次数；
- 提高 USART1 波特率（日志时间按比例缩短）；
- 计数与打印分离：计数常开，打印按需触发。

============================================================
六、遗留
============================================================

1. ISR 时间未归因
------------------------------------------------------------
- uxTaskGetSystemState 只统计任务运行时间，中断服务不进入
  任何任务；
- 两份日志各任务百分比之和约 97%，缺口即 ISR + 内核开销，
  目前未单独量化。

2. fc（ReID）路径未验证
------------------------------------------------------------
- 两份日志里 [PROF fc] 都是 n=0（本场景未触发识别）；
- wall 修正对 fc 的代码是同一处改法，但数值未上板验证。

3. AITask 栈余 2008 B
------------------------------------------------------------
- 该值与更早同场景的 6304 B 不同，说明本次走过更深的调用路径；
- 但 ON/OFF 两份 A/B 日志完全一致，说明不是本次改动引入；
- 栈仍余约 1.9 KB，列入后续观察项，不作为本次问题处理。

============================================================
七、复现
============================================================

1. 基准版本（profiling ON）：
   profiling.h 保持 PROFILING_ENABLE 1，make all -j8，EXITCODE=0；
2. 对照版本（profiling OFF）：
   临时改为 0，重新构建并烧录，抓同一场景日志；
3. 测完必须恢复 1 并重新构建，git diff 确认无 0 残留；
4. 对比方法：
   - 各任务百分比与 window 取多个窗口的均值；
   - wall 与 infer 按同一窗口配对，检查差值是否为固定小量。
