## 二、简历条目（润色版，可直接替换）

**智能元器件储物柜 · 主控软件负责人** 　　　　　　　　　2026.05 – 2026.08

**项目背景：** 面向实验室物料管理的端-边-云系统。柜体侧以 STM32N647 为主控，运行 FreeRTOS + LVGL，负责触摸交互、摄像头预览、离线人脸识别开柜、传感器采集与电磁锁控制；ESP32-C3 作为通信桥接，经 MQTT 与云端小程序交互，下发开柜、灯光、库存指令并上报柜体状态。

**我的职责：** 团队项目，我负责 STM32N647 侧的整体软件架构与落地，包括 RTOS 任务划分与同步、IMX335 → DCMIPP → LTDC 图像通路、BlazeFace + MobileFaceNet 的边缘部署、SD NAND 持久化，以及与 ESP32 的串口协议。

- **RTOS 架构与稳定性：** 按传感、图像、UI、通信、存储把系统拆成 10 余个任务并分级优先级，用信号量做帧、库存、姓名的跨任务同步，用互斥锁保护 I2C2、存储与 UI 全局变量，把中断与业务解耦；定位并解决高优先级 AI 任务忙等导致 LVGL 饿死、UI 线程硬杀 AI 线程可能打断共享资源临界区两类 UI 卡死问题，空闲 CPU 从 0% 恢复到 27%–33%。
- **图像通路：** IMX335 经 DCMIPP 双管道硬件分流，输出 800×480 RGB888 预览与 128×128 AI 输入；LTDC 双图层 + ColorKeying 把检测框画到独立透明层。用 DWT 周期级计时把「检测框缺角 + 30 Hz 闪烁」定位为采集与绘制共用帧缓冲的竞争：先用最小实验排除停流因素，再对比双缓冲、三缓冲 + VSYNC、覆盖层三种方案，最终选择覆盖层——每帧停流 14.3 ms 降至 0，绘制 134 µs → 约 300 µs，AI 任务 CPU 98% → 55%，预览稳定 30.7 fps。
- **边缘 AI：** 在 STM32N647 内置 Neural-ART NPU 上部署 BlazeFace + MobileFaceNet，完成 int8 模型接入、anchor 解码 + NMS、时域平滑与 5 帧取 2 的 K-of-N 投票；自建 DWT 逐 epoch 计时基座，把推理拆成 SW / Hybrid / Internal / HW 四类，实测检测 19.0 ms/帧（网络推理 15.9 ms，纯硬件占 73.2%）、识别 171 ms/次（CPU 回退 143 ms，占 83.9%），定位 PReLU 与量化/反量化算子为主要瓶颈。
- **存储与端云通信：** 接入 I2C / SPI / UART / ADC / TIM 等外设驱动；基于 SD NAND + FATFS，用脏标志 + 2 s 延迟落盘 + 互斥保护实现库存、人脸库与历史记录持久化；串口主链路采用中断 + 1 KB 环形缓冲解耦收发，设计 0xA5 帧头 + 长度 + 校验的状态机解帧与周期心跳，配合 ESP32-C3 实现 MQTT 云端指令下发与状态上报。

**技术栈：** STM32N647（Cortex-M55 + NPU）、FreeRTOS、LVGL、DCMIPP / LTDC / XSPI、ESP32-C3、MQTT

## 四、面试口述稿

### 4.1 30 秒电梯版（自我介绍里带过）

> 我讲一下智能元器件储物柜这个项目。它是一个面向实验室物料管理的端-边-云系统：柜体上有触摸屏、摄像头、电磁锁和温湿度、测距这些传感器，STM32N647 做主控，跑 FreeRTOS 和 LVGL；ESP32-C3 负责把数据通过 MQTT 送到云端小程序。我在团队里负责 STM32 侧的整体软件，包括 RTOS 任务架构、摄像头到屏幕的图像通路、离线人脸识别的部署，以及存储和串口通信。最后整机做到了人脸识别开柜、库存自动增减、云端能看状态；相机预览稳定在 30.7 帧，AI 任务的 CPU 占用从 98% 降到 55%。

### 4.2 90 秒标准版（项目单独介绍）

> 这个项目的背景是实验室的元器件管理：以前借还料靠手写登记，找料、盘点都麻烦，所以我们做了一台带人脸识别和库存管理的智能柜。
>
> 整个系统分三层：柜体侧是 STM32N647，负责触摸 UI、摄像头预览、人脸识别、传感器和电磁锁；中间是 ESP32-C3，做串口到 MQTT 的桥接；云端是小程序，能看到库存、温湿度、借还记录，也能远程开柜。
>
> 主控侧我按数据流拆了四块。第一块是 RTOS 架构：传感、图像、UI、通信、存储拆成 10 多个任务，用信号量和互斥量把中断和业务解耦。第二块是图像通路：IMX335 进来以后，用 DCMIPP 两个 pipe 硬件分流，一路 800×480 给屏幕，一路 128×128 给 AI；LTDC 两个图层，摄像头一层、UI 和检测框一层，用 ColorKeying 做透明叠加。第三块是边缘 AI：BlazeFace 检测人脸，MobileFaceNet 出特征做 1:N 识别，带 anchor 解码、NMS、时域平滑和 5 帧取 2 的投票。第四块是存储和通信：库存、人脸库、历史记录落在 SD NAND 上，串口用环形缓冲加状态机解帧，和 ESP32 走心跳。
>
> 我自己印象最深的是图像通路那个问题：检测框一直缺角、30 Hz 闪。我先用最小实验把「停流」这个因素排除掉，再用 DWT 算时序，确认根因是采集和绘制共用同一块帧缓冲；对比了双缓冲、三缓冲加 VSYNC、覆盖层三个方案，最后选覆盖层，因为它在物理上把采集和绘制隔离开了，改动也最小。结果是每帧 14.3 ms 的停流归零，AI 任务 CPU 从 98% 降到 55%，预览稳定 30.7 帧。

### 4.3 深挖版：按模块展开

> 下面这套是「面试官说“你详细讲讲”」时用的。每个模块都按同一节奏：**这块是干什么的 → 我怎么做 → 遇到什么困难 → 有哪些候选方案 → 为什么选这版 → 结果和代价**。

#### 模块 A：RTOS 架构与稳定性

**这块是干什么的。** 整机要同时做触摸 UI、摄像头采集、AI 推理、温湿度和测距轮询、条码枪、电磁锁、存储落盘、串口收发。裸机大循环做不到：UI 会卡，AI 一跑就断流，所以必须上 FreeRTOS，把「时基」「数据流」「人机交互」「通信」「持久化」拆开。

**任务怎么拆、优先级怎么定。** 我按「谁对时间最敏感」来分级：

| 任务 | 优先级 | 职责 |
|---|---|---|
| Encoder_Task | Normal + 2 | 编码器采样，旋钮要跟手，放在 Sensor 之上 |
| Sensor_Task | Normal + 1 | IMX335 初始化、DCMIPP 采集、帧同步 |
| AI_Task | Normal + 1（按需创建） | 等帧信号量 → 预处理 → NPU 检测 → 后处理/画框 → 识别 |
| LVGL_Task | Normal | 5 ms 周期跑 `lv_timer_handler` |
| Barcode / UART4_Rx | Normal | 条码枪、ESP32 串口收帧 |
| Aht10 / VL53L1X / Battery | Low ~ Normal | 温湿度、测距、电量 |
| StorageFlush | Low | 每 2 s 把脏数据落盘 |
| Stats | Low | 每 1 s 打一次各任务 CPU 占比和栈高水位 |

另外电磁锁、RGB 灯、打印机、出库流程是按需创建的，用完就退出，不常驻。

**任务之间怎么同步。** 主要是三类：

- `cam_frame_sem`：DCMIPP PIPE2 写完一帧释放，AI 任务阻塞等它。这是把「轮询」改成「事件驱动」的关键。
- `inventory_sem` / `face_name_sem`：条码枪和串口收姓名之间的交接。
- 互斥量：`i2c2_mutex` 保护触摸屏和摄像头共用的 I2C2；`storage_mutex` 保护 SD 卡读写；`flow_var_mutex` 保护 EEZ Flow 的 UI 全局变量。

**困难 1：LVGL 被饿死，UI 不响应。**

- **现象：** 一进相机页、画面里有人脸，UI 就明显卡；串口统计里 AITask 98%、IDLE 0%、LV_Task 只有 1%。
- **定位：** AI 任务优先级是 Normal + 1，比 LVGL 的 Normal 高；它的循环里又在忙等，而且每帧还要 Stop/Start 一次 PIPE1，光停流就 14 ms。等于 AI 把 CPU 占满了，LVGL 只能捡缝隙跑。
- **候选方案：**
  1. 把 LVGL 优先级提到 AI 之上——治标，AI 还是占满 CPU，而且 UI 和 AI 抢 DMA2D 会更严重；
  2. AI 循环里加固定 `vTaskDelay`——帧率不稳，CPU 还是浪费；
  3. 让 AI 阻塞在「相机帧信号量」上，帧到了才跑——把忙等改成事件驱动。
- **为什么选 3：** 它没有改动优先级关系，只是让 AI 在没帧的时候真正让出 CPU，符合「数据流驱动」的本质。
- **结果：** AITask 从 98% 降到 55%，IDLE 从 0% 回到 27%–33%，LV_Task 从 1% 回到 4%，帧率还是 30.7 fps，没有掉帧。

**困难 2：退出相机页偶发 UI 卡死。**

- **现象：** 从相机页返回主界面，偶尔整个 UI 不响应。
- **定位：** UI 线程用 `osThreadTerminate` 硬杀 AI 线程。AI 线程可能在用 DMA2D 画框，也可能持有共享资源；如果这时被杀在临界区里，FreeRTOS 不会替它释放锁，LVGL 的 flush 再用 `osMutexAcquire(osWaitForever)` 就会永久阻塞。
- **候选方案：**
  1. 启用 `dma2d_mutex` 再硬杀——死锁风险反而变大；
  2. 改成协作式退出：置一个退出标志，AI 任务自己在循环边界退出——最干净，但要改所有调用点；
  3. 当期先不启用这个互斥量，退出时调 `ai_clear_overlay()` 清掉残留框，AI 重启时把擦除表 `s_rect_n` 归零——改动最小、风险最低。
- **为什么选 3：** 这是一个「先止血、再根治」的取舍。协作式退出是正确方向，但涉及所有 UI 调用点，放在当期会拖慢主线；先把可复现的卡死消掉，把协作式退出列为后续独立任务。
- **结果：** 退出、重进相机页不再残留绿框，UI 不再卡死。
- **新学到：** RTOS 里「能杀」不等于「该杀」。共享资源 + 强制终止是死锁的温床，线程退出最好走协作式。

#### 模块 B：图像通路（IMX335 → DCMIPP → LTDC）

**这块是干什么的。** 摄像头要同时喂两个消费者：屏幕要 800×480 的实时预览，AI 只要 128×128 的输入。如果让 CPU 去缩放，根本扛不住，所以用 DCMIPP 两个 pipe 做硬件分流：

- PIPE1 → `g_ltdc_framebuf`，800×480 RGB888，直接给 LTDC 图层 0 显示；
- PIPE2 → `nn_input_u8`，128×128，给 AI 做输入。

LTDC 这边两个图层：图层 0 是摄像头，图层 1 是 LVGL 的 UI（RGB565）。进相机页时打开图层 1 的 ColorKeying，把 `0x0000`（黑色）当透明色，这样 UI 的空白处会透出下面的摄像头画面，检测框画在图层 1 上就自然叠在预览之上。

**困难：检测框缺角，还 30 Hz 闪。**

- **现象：** 检测到人脸后，绿色框和 6 个关键点下半部分时有时无，框像被「啃掉一角」。
- **原实现：** 画框前后各 Stop/Start 一次 PIPE1，想「暂停采集，别让下一帧把框覆盖」，框直接画进图层 0 的采集缓冲。
- **第一步，先做最小实验：** 只删掉 Stop/Start 两行，其他都不动。结果 `dstop` 从 14.3 ms 降到 0，`draw` 从 13.7 ms 降到 131 µs——**但框还是缺角**。这就排除了「停流导致缺角」的假设：停流只是浪费 CPU，不是根因。
- **第二步，算时序找根因：** PIPE2 写完释放信号量，AI 开始预处理 2.08 ms、推理 15.85 ms，等框画出来已经是帧开始后约 18.6 ms；相机一帧 33 ms，这时已经扫过约 56% 的行，本帧剩下的 44% 会把框的下半部分重新写成画面。**根因是采集和绘制共用同一块 buffer**，跟停不停流无关。
- **候选方案：**
  1. **双缓冲（DBM）：** 采集写 A、显示 B。但换址要等一个场周期（16.8 ms）才生效，期间还是会撕裂；框仍然是推理完才画，30 Hz 闪不会消失。要彻底干净得上三缓冲 + 在 VSYNC 时刻切采集地址。
  2. **三缓冲 + VSYNC 选址：** 最干净，但要改链接脚本、DCMIPP 地址切换和同步逻辑，工作量和风险都大。
  3. **覆盖层：** 框画到图层 1，DCMIPP 只写图层 0，物理上不可能被采集覆盖；ColorKeying 让空白处透明；不新增缓冲、不改链接脚本和 DCMIPP 配置。
- **为什么选 3：** 前两个方案都在「怎么让同一块 buffer 不被覆盖」上打转，第三个直接换思路——**让它们不共用 buffer**。而且改动集中在一个绘制函数和一个擦除表，风险最小。
- **代价：** 图层 1 和 LVGL 共用，得自己擦上一帧的框。做法是记录「裁剪后的矩形」，先擦后画；擦除就是往图层 1 填 `0x0000`，不用保存背景。另外 LVGL 的 dirty area 可能临时盖住框，但相机页 UI 很静态，实际影响很小。
- **结果：** `dstop` 14.3 ms → 0，`draw` 134 µs → 约 300 µs（占帧预算 0.9%），AITask 98% → 55%，预览 30.7 fps，框和关键点完整、不闪。
- **遗留：** 框仍然是推理结束后才画，视觉上滞后约一帧（33 ms）；要接近零延迟，得做三缓冲 + VSYNC 选址，那是另一个量级的改动。
- **新学到：** 排障先做最小实验分离变量，别一上来就加缓冲；「加缓冲」不是万能药，先看物理上能不能隔离。

#### 模块 C：边缘 AI（BlazeFace + MobileFaceNet）

**这块是干什么的。** 柜子要离线做人脸识别，不能依赖云。整条链路是两级模型：

1. **BlazeFace：** 检测人脸框 + 6 个关键点；
2. **MobileFaceNet：** 把人脸裁成 112×112，出 128 维 embedding，做 1:N 比对。

注册时多帧采集、做质量筛选；识别时连续 5 帧投票，至少 2 帧通过才开柜（K-of-N，`VOTE_N = 5`、`VOTE_K = 2`）。

**部署链路。** PC 端训练、int8 量化，LL_ATON 生成 C 代码，板上调 NPU 推理。DCMIPP 输出的是 BGR，模型训练用的是 RGB，所以软件里做 BGR→RGB 和 `/255` 归一化，这一步 196 KB 大概 2.08 ms。检测输出做 anchor 解码 + NMS，再按关键点裁人脸、量化成 int8 送 MobileFaceNet。

**为什么是 5 帧取 2。** 单帧会被侧脸、遮挡、运动模糊带偏，一次误判就开柜风险太大；5 帧里至少 2 帧通过，兼顾响应速度（5 帧约 165 ms）和稳定性。3/5 更严，但解锁延迟明显增加；2/5 是实测下来误识率和体验比较平衡的点。

**困难：识别一次要 171 ms，感觉慢。**

- **怎么定位：** 自建了一套 DWT 逐 epoch 计时。LL_ATON 的 runtime 在每个 epoch block 的 `PRE_START` / `POST_END` 上打点，按 **SW / Hybrid / Internal / HW** 四类累计，再和 `wall` 对账，确保计时点成对、没有漏配。
- **实测结果：** 识别一次 171.4 ms，其中 `call` 149.4 ms、`wfe` 21.7 ms；183 个 epoch 里，**107 个纯 SW 占了 143 ms（83.9%）**，73 个纯 HW 只占 27 ms（15.9%）。也就是说，慢的不是 NPU，是 CPU 回退。
- **再往下拆：** 110 个回退 epoch 里，DequantizeLinear 37 个、QuantizeLinear 33 个、PReLU 33 个，合计 103 个，占 94%。PReLU 是逐元素算，量化/反量化是数据搬运，正好都是 CPU 不擅长的活。
- **候选优化：**
  1. 换更小的模型 / 降输入分辨率——精度掉、识别距离变短；
  2. 重新导出模型，把 PReLU 换成 NPU 友好的激活、合并量化/反量化算子——从根上减少 CPU 回退，但要 PC 端重训/重导出，工作量大；
  3. 多帧并行 / 流水线——NPU 是单核，收益有限。
- **为什么当期没做：** 这一轮的目标是「先把现状测准」，不是「为了简历造一个优化后的数字」。测量基座和瓶颈定位做扎实了，下一步直接按方案 2 做重导出，再用同一套基座复测，前后对比才有意义。
- **顺带一个对比：** 检测路径正好相反，19.0 ms/帧里推理 15.9 ms，纯 HW 占 73.2%，是硬件主导；所以检测不是瓶颈，识别才是。
- **新学到：** 「NPU 占比」要区分**计数占比**和**时间占比**。这个模型纯 HW 的 block 数占 39.9%，但时间只占 15.9%，两个数说的不是一回事，面试和简历上都要标口径。

#### 模块 D：存储与端云通信

**存储这块。** 要存三类数据：28 个主柜 + 6 个副柜的库存、人脸库、借还历史。方案是 SD NAND + FATFS，每个文件整包重写。

- **困难：** 如果每次库存变动都立刻写，UI 会阻塞，SD 的写放大也难看。
- **候选方案：**
  1. 立即写——简单，但卡 UI；
  2. 日志式追加——写得少，但解析和垃圾回收复杂；
  3. 脏标志 + 延迟落盘——改动小，把写操作集中到低优先级任务。
- **选 3：** 每个数据模块置 dirty 标志，`StorageFlush` 任务每 2 s 检查一次，有脏数据才写，写的时候拿 `storage_mutex`。代价是最多丢 2 s 的数据，对库存场景可接受。
- **结果：** UI 不再被 SD 写阻塞，库存/人脸/历史重启后都能恢复。

**通信这块。** STM32 和 ESP32-C3 走 UART，帧格式是 `0xA5 + type + len + payload + checksum`。

- **收：** 中断里只把字节塞进 1 KB 环形缓冲，任务里跑状态机逐字节喂，避免在中断里做解析；帧头同步 + 长度字段 + 校验，错帧/半包能自动复位。
- **发：** 按 type 组帧，温湿度、电压、人脸注册/识别事件、出入库、历史记录各有各的 type。
- **心跳：** ESP32 周期发 `0x05`，STM32 记 `last_heartbeat_tick`，超时就把 ESP32 标离线；云端下发的开柜、灯光、库存、时间同步都走同一个分发表。
- **困难：** 串口最容易出的是粘包、错帧、半包。解决思路不是「加大缓冲」，而是「帧头 + 长度 + 校验 + 状态机」，让解析器自己能从任意字节流里重新同步。

#### 模块 E：外设驱动（一句话带过，等追问再展开）

> 外设这块我接入了 I2C / SPI / UART / ADC / TIM：AHT10 温湿度、VL53L1X 测距、编码器、电池电压、电磁锁、RGB 灯、条码枪。触摸屏和摄像头共用 I2C2，所以加了一把 `i2c2_mutex`；电磁锁和 RGB 灯是按需创建的任务，开柜时拉高、延时、复位，不常驻占资源。

## 五、高频追问与答法

> 原则：先给结论，再给一句证据，最后给一句取舍。不要背长段。

**Q1：为什么用 FreeRTOS，不用裸机大循环或 RT-Thread？**
> 裸机大循环做不到「UI 一直响应 + 摄像头一直采集 + AI 随时跑」，一个长任务就会把其他事情堵死。FreeRTOS 在我这个芯片上移植成熟、RAM 占用可控，而且我需要的是任务隔离和优先级，不是文件系统/网络协议栈那一整套。RT-Thread 也能做，但团队已有 FreeRTOS 的驱动和调试积累，换栈的收益不大。

**Q2：任务优先级怎么定？会不会优先级反转？**
> 按「错过截止时间的后果」定：编码器 > 采集/AI > UI/通信 > 存储/统计。共享资源用互斥量，FreeRTOS 的互斥量默认带优先级继承，能缓解反转；但我不会让高优先级任务长时间持锁，临界区都尽量短。

**Q3：为什么用信号量，不用消息队列或任务通知？**
> 我这里主要是「一帧到了，通知 AI 去取」这种一对一同步，信号量最直接；队列适合传数据块，任务通知适合一对一且不想额外分配对象的场景。选信号量是因为语义清楚、调试时能看到计数。**（如果简历写了队列/任务通知，这里要能说出具体用在哪；说不出来就按这个口径改。）**

**Q4：DCMIPP 两个 pipe 怎么配？为什么不让 CPU 缩放？**
> PIPE1 出 800×480 RGB888 直接写 LTDC 图层 0 的帧缓冲；PIPE2 出 128×128 给 AI。两路是硬件并行分流，CPU 只做 BGR→RGB 和归一化。让 CPU 从 800×480 缩到 128×128，一帧就是几十万像素的搬运，30 fps 根本扛不住。

**Q5：ColorKeying 是什么原理？为什么键控黑色？**
> LTDC 合成时，图层 1 里等于设定颜色（这里是 `0x0000`）的像素不参与混合，直接透出图层 0。选黑色是因为 UI 背景和擦除色都用 `0x0000`，擦框就是往图层 1 填黑，不需要保存背景，代价最小。注意这个功能只在相机页开，主界面开的话黑色 UI 元素会一起变透明。

**Q6：为什么不用双缓冲？覆盖层有什么缺点？**
> 双缓冲解决的是「采集写 A、显示 B」，但换址要等一个场周期才生效，期间还是撕裂；而且框是推理完才画，30 Hz 闪不会消失。覆盖层是换思路：DCMIPP 只写图层 0，框只写图层 1，物理隔离，不可能被覆盖。缺点是图层 1 和 LVGL 共用，要自己维护擦除表；LVGL 重绘可能临时盖住框，但相机页 UI 很静态，影响很小。

**Q7：检测框为什么滞后一帧？能消除吗？**
> 因为框要等推理结束才画，推理 15.9 ms + 预处理 2 ms，画的时候相机已经扫过大半帧了。要消除得做三缓冲 + 在 VSYNC 时刻切采集地址，让「显示的那块」和「正在采集的那块」彻底分开，成本和风险都高一个量级，当期没做。

**Q8：NPU 怎么部署？int8 量化怎么校准？**
> PC 端训练后做 int8 量化，LL_ATON 生成 C 代码，板上初始化网络、拿输入输出 buffer 调 `run`。校准集用的是实际场景的人脸/背景图，覆盖不同光照和距离；量化后重点看检测框有没有明显偏移、识别距离有没有掉。**（如果校准细节记不清，就说「校准集是队友按场景采的，我主要负责板上部署和后处理」，别硬编。）**

**Q9：anchor 解码和 NMS 怎么做？阈值怎么调？**
> BlazeFace 输出的是相对 anchor 的偏移和置信度，先按 anchor 解码成框，再做 NMS 去重叠；阈值是拿实测样本扫出来的，宁可略严一点，后面还有时域平滑和 K-of-N 兜底。

**Q10：K-of-N 为什么 5 取 2？误识率和速度怎么权衡？**
> 单帧容易被侧脸、遮挡带偏，5 帧取 2 是在「解锁延迟约 165 ms」和「误识率」之间折中。3/5 更稳但更慢；2/5 实测误识率可接受。这个参数是暴露在头文件里的，现场可以按场景调。

**Q11：识别 171 ms 怎么优化？为什么没做？**
> 已经定位到是 CPU 回退占 84%，主要是 PReLU 和量化/反量化算子。优化方向是重新导出模型、换 NPU 友好的激活、合并量化算子；当期先把测量基座和瓶颈定位做扎实，没有为了数字去改模型。下一步优先做重导出，再用同一套 DWT 基座复测前后对比。

**Q12：脏标志延迟落盘，掉电怎么办？**
> 最多丢 2 s 的库存变动。这个场景的写入频率不高，2 s 是可接受的；如果要求更高，可以缩短周期，或者对关键记录（比如开柜事件）改成立即写。当前没有做掉电检测，这是可以改进的点。

**Q13：串口粘包、错帧怎么处理？**
> 中断只入环形缓冲，任务里状态机解析；帧头 `0xA5` 同步，长度字段定边界，校验失败就丢弃并重新找帧头。这样即使从字节流中间开始，也能自己重新同步。

**Q14：这个项目你遇到最大的困难是什么？**
> 检测框缺角那个。它难在「看起来像停流导致的，其实不是」。我先用最小实验把停流删掉，发现框还是缺，才逼着自己去算帧内时序，最后定位到共用帧缓冲。这件事让我养成了一个习惯：先做能推翻假设的最小实验，再动结构。

**Q15：如果重做，你会改什么？**
> 三件事：一是把 AI 线程改成协作式退出，彻底去掉硬杀；二是图像通路如果资源允许，上三缓冲 + VSYNC 选址，把视觉延迟压到一帧以内；三是识别模型重新导出，把 CPU 回退的算子换掉，并用同一套 DWT 基座做前后对比。

## 七、面试前 5 分钟速记卡

1. **一句话：** 端-边-云物料柜，STM32N647 主控，我负责 RTOS + 图像 + 离线人脸 + 存储通信。
2. **四个数：** 98%→55%、30.7 fps、检测 19 ms/帧、识别 171 ms/次（CPU 回退 84%）。
3. **一个故事：** 框缺角 → 最小实验排除停流 → 算时序定位共用缓冲 → 三方案选覆盖层 → 14.3 ms 归零。
4. **一个取舍：** 覆盖层 vs 双缓冲 vs 三缓冲，为什么选覆盖层。
5. **一个教训：** 硬杀线程 + 共享资源 = 死锁温床，协作式退出才是正解。
6. **一个诚实：** 识别优化只做了定位、没做模型重导出，不编「优化后」数字。
